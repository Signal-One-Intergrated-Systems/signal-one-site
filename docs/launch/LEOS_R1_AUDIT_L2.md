## 1. Verdicts

- **#704: PASS WITH CONDITIONS.** The receiver's security core holds under adversarial test: credential handling, uniform 401, revocation (incl. mid-request), tenant from credential only, tenant law, idempotency under 25-way concurrency, match-lock race, atomic rollback. **Merge** is blocked only by L2-05 (migration-number collision with `main`). **Launch as a working enquiry channel** is blocked by four S1s that are operational/privacy gaps, not exploitable defects: L2-01 (guard/sales applications have no reader), L2-02 (returning-company enquiries have no UI and nothing notifies anyone), L2-03 (erasure impossible; retention unset), L2-04 (no production credential issuance procedure).
- **#748: PASS WITH CONDITIONS.** The radio-quote allow-list fix is correct and necessary (without it every radio quote from the deployed site is lost). The decision to exclude `attribution` from the idempotency hash and keep the FIRST attribution is correct (see §3 item 4). Conditions: L2-08 (an optional attribution value can cost the whole enquiry) and L2-03 (attribution is an online identifier stored in an append-only table outside every erasure plan).

### Answers to the ten audit questions (where not already a finding)

1. **Authentication** — PASS. SHA-256 of a 256-bit secret only (`store.ts:88-96`); lookup by unique hash then `timingSafeEqual` on equal-length digests (`store.ts:106-111, :181-200`); shape check `^wic_[A-Za-z0-9_-]{43}$` before any query; one indistinguishable 401 for missing/malformed/unknown/revoked (tests 4, R4b); revoked mid-request → rollback + 401 (`touchCredential` with `status='active'` inside the tx, test 10e); credential scope = this route only, tenant bound at issue; Authorization removed from `req.headers` before anything can log it (test 10f, A6 with positive control P10). Gaps: L2-04, L2-09.
2. **Tenant isolation** — PASS, adversarially re-proven (L2-T6 + mutation M-L2-2): tenant only from the credential; tenant-like keys anywhere (headers, cookies, query, body at any depth, duplicate raw keys) → 422; every intake query carries `tenant_id`; idempotency key unique per `(tenant_id, key)`; a shared key across tenants yields separate records and never the other tenant's reference.
3. **Validation vs real website** — PASS for fields/intents (exact equality; history checked). One lost-enquiry path via optional attribution (L2-08). Note the journey forms restore drafts from localStorage unfiltered (`useJourney.ts:52-66`): a future field rename on the site will 422 every restored draft — keep the e2e pin.
4. **Idempotency** — PASS. Unique `(tenant_id, idempotency_key)`; canonical-body SHA-256 excluding the site's per-attempt stamps; same key + same hash → original receipt `duplicate:true`; different hash → 409 audited; 25-way parallel identical → 1 row (L2-T4); race past the lookup → answered as replay (test 10g). **#748 attribution exclusion: correct.** The site's key is per form-state and fingerprinted on kind+data+marketing (`app/lib/intake.ts:70-78`), so a same-key retry is by definition the same submission; first-write-wins keeps the ledger append-only and matches what was true when the enquiry was first recorded. Accepted consequence: a retry that first carries attribution after an attribution-less original keeps none.
5. **Lead matching** — correct and non-merging (candidates only, labelled unverified; nothing written to an existing lead); tenant-scoped (mutation-proven); race-safe (mutation-proven). Not qualified by any index (L2-07); Unicode-space miss (L2-10).
6. **Routing** — DB-enforced routing CHECK (`0187` `website_intake_submissions_routing_check`): 6 client intents → `crm_lead` (no candidate) or `website_enquiry` (candidate); `guard-profile` → `guard_applications`; `sales-representative-application` → `recruitment_applications`; receipt type fixed per kind. Guard/recruitment data is never visible to sales roles — because nothing reads it at all (L2-01). `marketplace-interest` → sales lead: justified only as a waitlist; purpose control is missing (L2-11).
7. **Privacy** — consent: processing required, marketing a separate row only when opted in, notice version validated and stored, `recorded_at` = site server time, `clientCapturedAt` validated but discarded. Attribution column: no application read path (write-only), so readable only by DB operators/backups; excluded from retention runs (non-dry refused) and from the erasure plan. Missing: L2-03, L2-11.
8. **Failure recovery** — DB failure mid-tx → 500, nothing kept, no hook (tests 8, 8b, dd319d7); crash after commit → retry returns the same receipt (`findSubmission` → `duplicate:true`); hook best-effort in memory (L2-06); per-credential limit shared in Postgres and fail-closed 503 (60/min per credential = whole website; the site turns 429/503 into 502 + mailto fallback); pre-auth failure gate in-memory per process by design (unauthenticated requests write nothing). Timeouts: L2-12.
9. **Migrations** — classes: 0187/0188/0190 create only new objects, no FK to a pre-existing table → **A correct**. 0191 alters 0190's tables and indexes 0187's ledger, guarded to refuse unless those are empty → **A defensible**. 0192 `ALTER TABLE … ADD COLUMN attribution jsonb` (nullable, no default: metadata-only) + `ADD CONSTRAINT CHECK` (validating scan under ACCESS EXCLUSIVE) on 0187's ledger **without an empty guard**: harmless if shipped with 0187 (L2-05 ordering), but its header's "creates only new empty objects" is not literally true if the ledger is populated; use `NOT VALID` + `VALIDATE` or add the empty guard. Reversals round-trip byte-identically and refuse when data exists. No migration locks a large existing table (`crm_leads`, `users`, `tenants` untouched).
10. **Sales OS visibility / minimum safe launch configuration** — queue: `website_queue.read/act` effective for stored `commercial_director` and `super_admin` (re-checked stored role, status and membership every request), and for stored `admin` users with a live per-user grant; `sales_manager` holds the permission in the matrix but no stored user signs in as it (maps to `sales_representative` → 403). **Minimum safe configuration:** (a) do NOT apply the Class B `sales_manager` mapping for launch; (b) at least one active stored `commercial_director` (or `super_admin`) with an active membership in the website's tenant, named as queue owner (L2-02); (c) no `website_queue`/`website_privacy` grants except to named human admins, with reasons; `privacy.manage` stays super_admin-only; (d) impersonation stays refused; (e) a credential issued to exactly the website's tenant (L2-04); (f) the restriction→CRM gap (ruling 7 hand-off, still open) accepted, since only `super_admin` (`crm.read`) and the assigned rep (`crm.own.read`) can read a restricted lead.
