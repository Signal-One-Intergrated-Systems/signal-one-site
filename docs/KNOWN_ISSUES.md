# Known issues

## KI-1 Intermittent hydration error (React #418) under load — ROOT CAUSE FOUND (W2, 2026-11-25)

- **What the visitor experiences:** a small share of page loads on a busy device log `Minified React error #418`. React then discards the server HTML of the whole page body and renders it again on the client. The page works afterwards: links, navigation, forms, validation and submission are all ordinary client code and behave normally. What is lost is anything that happened *before* hydration on that load: text typed into a field, focus, a running CSS entrance animation; images may flash as their elements are recreated. On the slow phone profile hydration finishes ~2–3 s after navigation, so the realistic customer impact is a rare visible re-render and, very rarely, a lost half-typed field. No data is sent wrongly and no enquiry can be submitted twice because of it. Severity **S3**.
- **Root cause (proven from the failing loads themselves):** an unminified production build of this branch (`experimental.turbopackMinify: false`, scratch only) was loaded under load (8 concurrent pages, 4× CPU) with React's `throwOnHydrationMismatch` instrumented in flight. Every hit had the same signature:
  - fiber: the `<div data-scene-route class="s1-scene-route">` rendered by `SceneTransition` (`app/components/SceneTransition.tsx`), a direct child of `<body>`;
  - DOM candidate React was trying to claim for it: that div's **own first child**, `<main id="main">` (with the real div present in `<body>`, correctly placed);
  - call stack: `throwOnHydrationMismatch ← beginWork ← replaySuspendedUnitOfWork ← renderRootConcurrent ← performWorkOnRoot ← performWorkUntilDeadline`.
  
  The div's child is the page itself, passed from the server layout as `children`: an RSC slot that, while the page payload is still being processed, is a pending lazy reference. When the div is the unit that suspends on it and the reference resolves within React's retry window, React **replays** the div's `beginWork`. In the React build bundled with Next.js 16.1.0 (and 16.1.7 — identical `19.3.0-canary-f93b9fd4-20251217`), `replaySuspendedUnitOfWork` does not rewind the hydration cursor for a host component (tag 5): the first attempt already claimed the div and moved the cursor to its first child, so the replay tries to match `<main>` against `<div>` and reports a mismatch. The React bundled with **Next.js 16.4.6** (`19.3.0-canary-278794d7-20261002`) adds exactly that rewind (`fiber === hydrationParentFiber && (popToNextHostParent(fiber), nextHydratableInstance = fiber.stateNode)`). It is load-dependent because it needs the page payload to resolve in a narrow window while hydration is running, which is what a slow or busy CPU makes likely.
- **Ruled out by the same evidence:** time/locale rendering, `useId`, viewport reads during render, `IntakeAvailability`'s fetch, the header's `scrolled` state, DOM changes by our own scripts (the `<body>` children were intact at the moment of failure: skip link, JSON-LD, header, the scene-route div, overlay, footer).
- **Fix on `wip/w2-perf` (app-side, no visual change):** `SceneTransition` now puts a function component (`RouteContent`, renders only its children) between the div and the slot. The unit that suspends and replays is then a function component, which claims no DOM, so the cursor stays correct. Server HTML is byte-for-byte the same shape (no extra element).
- **Measured (interleaved, same load for every build, 8 concurrent pages, 4× CPU, `/join/sales`@375, `/contact`@768, `/get-started`@1440, `/security-trust`@768):** an instrumented probe recorded which fiber suspends while each page hydrates (240 loads per build). **Unfixed:** the scene-route `<div>` suspended on 2 loads and was replayed on both; the only #418 in the run was on one of them. **With `RouteContent`:** the div never suspended (`RouteContent` took the suspension 145 times, as designed) and there were **0 × #418**. Plain rate runs without instrumentation gave 0/700 for the unfixed build, 0/700 with the fix and 0/700 on Next.js 16.4.6: at this machine's load the error is too rare to compare rates directly (earlier, the instrumented unminified build had 3 hits in ~430 loads). The fix is therefore shown by mechanism — the unit that fails can no longer be a host element — not by a rate difference.
- **Recommended next release (separate from launch, with the full suite):** upgrade Next.js to 16.4.x, which fixes the React bug for every host element, then remove `RouteContent`. Building 16.4.6 here needed one unrelated change: the fresh install's `@axe-core/playwright` pulled `playwright-core` 1.63, whose `Page` type no longer matches the pinned `@playwright/test` 1.56.1 in `visual-mission.spec.ts` (type check only). 16.1.0 is also eleven months old; later 16.x releases carry security fixes and should be reviewed for that reason alone.
- **History:** first seen as 2/336 vs 5/336 loads (`main` @ `fdbdfa2` vs R0) in `visual-mission.spec.ts`; a second build running beside the server made it 11/360 (removed from the suite, `tests/e2e/global-setup.ts`); 0/160 in isolation. All consistent with a CPU-timing-dependent framework bug.
- **Test policy:** the check that pages log no errors stays strict. It is not skipped, retried or loosened.
